A software factory,
staffed by
AI coding agents.

ConsensFlow is a desktop app. You give the goal to one agent, the Chief of Staff. It plans the work on a board, and a staff of workers, advisors, reviewers, testers and an image designer takes the tasks, each in a terminal of its own. Many exchanges later, what comes out is software, in your project.

It works through the coding agents you already use, Claude Code, Codex, OpenCode, Pi and Devin, with your own logins. It stores no passwords and needs no API keys.

A software factory

Behind the board, ConsensFlow is a small civilization at work. The chief plans and hands out tasks. Workers build, and ask the chief when a call is not theirs. Advisors bring findings. Reviewers check finished work and testers check it by running it, and when they find something the chief sends it back, into the same window, so the follow-up continues where the task stopped. The image designer draws the images the chief asks for. You set the goal and make the calls that are yours. What comes out is software.

One goal, start to finish

The shopping list of the demo project, as its chief ran it: your words in the chief's terminal, what the board carried between the chief and its staff, and the note that told you the work was in. It is the thread T-2 keeps, shown open under What it does.

  1. Goalyou → chief, in its terminal

    “The pantry app needs a shopping list: add items, check them off, clear what's done. Keep the list on the server, and have the API reviewed before the page is built on it.”

  2. Request 1chief → the board · T-2, for a standard worker

    The chief reads the routes the app has and writes the brief: three routes, where to keep them, tests beside theirs, npm test before reporting. It adds T-4, the page, to wait until T-2 is accepted. theia, a worker on Codex, is free: T-2 opens in a fresh Codex window.

  3. Questiontheia → chief · T-2 waits

    “Should clearing delete the checked rows, or keep them and mark them cleared? items keeps its history with a deleted_at column; the list could do the same.”

  4. Answerchief → theia · T-2 goes on

    “Delete them. The list is a scratch pad: nothing reads old entries, and items keeps the history that matters.”

  5. Result 1theia → chief · T-2 done, for the chief to decide

    “Done. The three routes are in server/routes/list.ts, mounted in server/app.ts. […] 15 new tests in server/routes/list.test.ts. npm test passes: 61 tests.”

  6. Reviewchief → the board · T-3, for a complex reviewer

    “Read the change for T-2 and the diff. Is it right, and is it tested?”

    seshat, a reviewer on Devin, takes it. A review changes no file.

  7. Findingsseshat → chief · T-3 done

    “Not ready yet: two findings. Clearing deletes row by row, outside a transaction; a failure halfway leaves the list half cleared. PATCH with an unknown id throws, so the client gets a 500; it should get a 404. Otherwise the routes match the brief, and each has its tests.”

  8. Request 2chief → theia · T-2 reopened, back into the same window

    “The review (T-3) found two things to fix before I accept this: clear it in one transaction, and answer 404 for an id that does not exist. Add a test for each, run npm test, and report.”

  9. Result 2theia → chief · T-2 done again

    “Both fixed. Clearing runs in one transaction: a failing delete rolls the whole clear back. An unknown id answers 404. 3 new tests. npm test passes: 64 tests.”

  10. Acceptedchief · T-2 and T-3 finished

    T-4, the page, was waiting on T-2: it starts now, in a window of its own.

  11. Notechief → you, on the board

    “The shopping list API is in: T-2, reviewed in T-3. The page is under way in T-4.”

And it goes on. For the expiry reminders, the chief had a question of its own, how to handle time zones, and put it to the advisor as T-6. Three findings came back, and the chief turned them into the next tasks: store each household's time zone, T-8, then the reminders themselves, T-9, waiting on the page, the advice and the time zone. It is all there to read in the first capture above, in the chief's terminal.

How it works

Everything happens in one window: the board on the left, the agents' terminals on the right. Here is one task's path across the board.

  1. Backlog
  2. Queued
  3. Working
  4. Waiting
  5. Done
  6. Finished
T-5 Shopping list page Working
    • Backlog

    The chief puts a task on the board

    A brief written for someone who has never seen the project, and the tier the work needs: critical, complex, standard or light. A task can wait for others to be accepted first.

    • Queued

    A free member of that tier takes it

    ConsensFlow gives the task to a free member of the tier, never to a name, so the work is shared across the staff. A member runs as many tasks at once as it is given.

    • Working
    • Waiting

    It works in a terminal of its own

    A fresh terminal of the member's harness, with your login. Open it from the member's row to watch, or send it an urgent word. A question to the chief puts the task in Waiting until the answer comes.

    • Done
    • Finished

    The result comes back to the board

    The chief decides: accept it, or send it back to the same window with what must change. The window closes, and the task keeps everything its agent wrote.

What it does

The staff

One chief, a whole staff
Give the chief your goal in its terminal. It reads the project, plans and decides, and every change goes to the staff you picked as a task, however small.
Workers, advisors, reviewers, testers and an image designer
Workers do the tasks. Advisors answer the chief's questions with findings. Reviewers check finished work, and testers check it by running it. The image designer draws an image with its harness's image tool and saves it where the task says. Advisors and reviewers never change a file, and testers change no product code.

The agents

Ready-made, or your own
An agent is a harness, a model and an effort. Settings → Agents lists ready-made ones, grouped by the tier of work they are for, and lets you define your own with any model your harness accepts. The versions of each harness that work are on the Supported versions page.
Switch the chief anytime
Move the chief to another agent or harness. The new chief starts with a handoff: what is on the board, your last words, and the history of the chiefs before it.

The board

A board you can read
Each task shows who has it and where it stands, from backlog to done. Open a task to read its brief, its result, and everything its agent wrote.
Each task in its own window
A task opens a fresh terminal of its agent's harness, and the window closes when the work is done. Its conversation is kept, so a follow-up continues where it stopped.
Plans with an order
A task can wait for others to be accepted first, so a plan of many tasks runs in its own order, in parallel where it can.

Specs

Big work becomes a spec
With specs on, the chief plans big work as a spec, with Specmint, and puts each phase on the board as tasks, in order. A small ask still goes straight to the board. It uses the Specmint its harness has, or a copy ConsensFlow brings.
On for every project, or for one
Specs are off until you turn them on. Settings → Specs turns them on for every project, with the folder and the Specmint variant they use unless a project names its own. A project's own settings win.
Read them in the app
The Specs button on the board opens the project's specs folder: its tree, the registry as rows, and each spec as Markdown, Mermaid diagrams included. HTML specs open in your browser, from a copy.

History

Everything a participant said New in 3.0.6
The History button on a window's head, and beside Switch chief, opens everything ConsensFlow keeps of that participant: its whole stored transcript, across chief switches, /clear, /resume and compactions. Search it. Tool output shows on request, and what ConsensFlow delivered folds to one line.
The chief reads it too
After you switch the chief, the new one reads what you and the chiefs before it said with cf history, and searches it with --find.

Wake-up calls

A nudge on a schedule you set
A chief that stopped while work is left carries on. In Project settings you set how often it is asked, and what it says: “Do you still have work to do?” by default.
Only when it helps
A wake-up goes in only while the chief is at rest and you have nothing typed in its window, never while the project is paused, and never two at once. If one changed nothing on the board, the next waits until something moves.

Project settings

One dialog for each project
Project settings holds the project's staff, human approval, wake-up calls and specs. The board's button opens it, and so does the project's menu in the sidebar. New project offers the same, so a project can start with them set.
The project menu
Right-click a project in the sidebar to rename it, or to give it a one-line description, shown under its name. The description is yours alone: no agent is told it.

You stay in charge

Pause, resume and tell
Stop any task and keep its window and work, or send an urgent word into a window mid-task.
Quota-aware
When an agent runs out of quota, its task waits for the reset or goes to another member of the same tier.
Your approval, if you want it
Turn on human approval for a project, and every message between agents waits for you to pass it on.

Install

Download ConsensFlow for Mac or Windows. It works with the coding agents you already have, Claude Code, Codex, OpenCode, Pi or Devin, each signed in once in a terminal. One is enough to start. Everything else it needs comes with it.

Your data, and what the agents can do

  • ConsensFlow keeps its data in ~/.consensflow (on Windows, %USERPROFILE%\.consensflow).
  • It never sees your passwords: each agent uses its own harness's login.
  • Agents work with full permissions in their windows, as they would if you ran them yourself. Your protection is the review, the chief's acceptance and, if you turn it on, your approval. Use ConsensFlow on projects kept in version control.
  • Every agent, the chief and its staff alike, starts with its harness's MCP servers and connectors, skills, settings and customizations, as it would if you ran it yourself. The staff use them with full permissions while you aren't watching, so keep in a harness only what you would let any agent use.
